About this demo

A viral post claimed AliExpress was secretly recording audio. It wasn’t. What’s actually happening is more interesting, entirely permissionless, and follows you into incognito.

Watch it happen

A name is registered in a normal window, then the same URL is opened in a fresh incognito window: no cookies, empty localStorage, no login — and the page still names the visitor, because both windows produce the same device hash.

What the original story really was

Someone noticed their Bluetooth headphones stopped switching between devices whenever an AliExpress tab was open. The tab was holding an audio output stream open. That got relayed online as “AliExpress is secretly recording you,” which is wrong in a specific way worth understanding:

 what people heard              what is actually happening
 ─────────────────────          ──────────────────────────────────────────────
 microphone recording           speaker-side playback only, at zero volume
 audio uploaded to servers      only a ~64-character hash leaves your machine
 works silently, no consent     true — and that is the actual problem

A web page cannot capture your microphone without getUserMedia, which forces a permission prompt and lights the recording indicator in your tab and OS. Across 20 instrumented sites — with every microphone-capable API hooked before any page script ran — there were zero calls. The fingerprinting graph has no input node at all.

The mechanism, in detail

1. Generate a signal

The script creates an oscillator (a pure ~10 kHz tone) and runs it through a DynamicsCompressor — a non-linear processor whose output depends on floating-point maths performed by your CPU and the browser’s audio stack.

2. Render it where nobody can hear

Usually this happens in an OfflineAudioContext: the graph is computed straight into a buffer, faster than realtime, and never sent to a speaker. Nothing plays, nothing is recorded, no permission is required.

3. Read the processed samples

The script sums the absolute values of a slice of the rendered buffer. Different devices produce values that differ in the low-order digits — enough to distinguish machines, and stable enough on the same machine to be an identifier.

4. Combine and hash

That number is mixed with other permissionless signals — your GPU’s renderer string via WebGL, screen size and colour depth, CPU core count, platform, timezone, and (for the more precise variant) how your machine rasterises a line of canvas text — then hashed with SHA-256.

 hardware id = sha256( audio ## webgl ## screen/cpu/platform/timezone )
 full id     = sha256( audio ## webgl ## screen/cpu/platform/timezone ## canvas )

 hardware id → survives a new browser profile, sometimes a different browser
 full id     → more unique, but changes between browser engines

Deliberately excluded: devicePixelRatio. It changes with page zoom, and zoom is per-profile, so including it would break recognition for anyone who had zoomed in.

The badge, and the city

The demo gives every device an emoji and a colour. Neither is stored anywhere: they are read straight out of the first bytes of the hardware hash, so the same machine draws the same badge in a normal window, in incognito, and often in a completely different browser. It is the same link the name lookup makes, just visible at a glance.

 hardware id  5f1c9a…      badge  = emoji[ 0x5f1c % 24 ]  +  colour[ 0x9a… % 8 ]
                                    same device → same badge, every time

The city comes from your IP address, which every request carries by definition — there is no navigator.geolocation call, so there is no location prompt to decline and no indicator. Hosted on Vercel, the edge network hands the server a city and region header before any code of mine runs; run locally it falls back to a keyless IP lookup. It is city-level, frequently wrong by a metro area, and this demo never stores it.

Put together, that is the uncomfortable part: a page you have never logged into, that set no cookie, can greet you with a stable identity and a rough location in the first few hundred milliseconds.

The realtime variant — the Bluetooth bug

A minority of sites (AliExpress and, surprisingly, eBay in my run) don’t use the offline path. They create a realtime AudioContext and connect the graph through a zero-gain node to context.destination, then never close it.

 (A) classic offline hash              (B) realtime destination-connected
     OfflineAudioContext                   realtime AudioContext
     osc → compressor → render             osc → … → gain(0) → DESTINATION
     runs once, releases the device        stays RUNNING for the tab's life
     no side effects                      OS thinks audio is playing
                                          → holds the Bluetooth A2DP link
                                          → multipoint switching stops working

Why realtime at all? Because a graph is only actively rendered while it is connected to the destination, and the measurement callbacks these scripts use only fire during that rendering. The speaker hookup is what drives their loop. Muting the tab doesn’t help: mute applies to media elements, not Web Audio graphs.

To be precise about what I did and didn’t observe: the realtime path keeps an output stream and the local measurement loop alive. I did not observe audio, or continuous streams of data, being uploaded anywhere.

Why this is worth worrying about

Not because of microphones — because it is a super-cookie that you cannot see, clear, or decline. It needs no consent banner and shows no indicator. It survives incognito, clearing cookies, and often a change of browser. And because the same handful of anti-fraud vendors supply it to hundreds of unrelated sites, one stable ID can link the same person across all of them.

To be fair about the other side: these scripts are mostly there to catch fraud and bots, and a fingerprint is genuinely useful for that. The problem is that the exact same signal works just as well for tracking, and nothing in the browser tells you which is happening.

Honest limits of this demo: it maps a name you typed to a device hash — it doesn’t discover your real identity out of thin air (a real tracker gets that by linking the fingerprint to an account or an ad-network profile). Matching across two different browser engines is unreliable, especially on machines using software rendering.

Sites doing this today

From a single instrumented run of 20 major shopping sites (Firefox + Chromium, August 2026). Bot-detection scripts branch per session and region, so treat this as “observed at least once,” not a permanent property of each site.

BehaviorSites
Held a live audio path open to the speakers (zero volume, never closed — this is what broke the original reporter’s Bluetooth) aliexpress.com, ebay.com
Ran the one-shot offline audio hash temu.com, shein.com, shopee.com, dhgate.com, banggood.com, walmart.com, ebay.com
Shipped audio-fingerprinting code that didn’t fire during my visit alibaba.com, lazada.com (same Alibaba script), amazon.com (via AWS WAF)
Other fingerprinting only (canvas, WebGL, device attributes) — no audio taobao.com, tmall.com, wish.com
Nothing observed jd.com, miniinthebox.com

It is not a China story: US eBay held the live audio path open exactly like AliExpress, while Chinese JD.com came back clean. It’s the shared anti-fraud vendors (Alibaba’s fireyejs, HUMAN/PerimeterX, AWS WAF) that spread it — which is also what makes one fingerprint useful for linking you across unrelated sites. No site I tested touched the microphone.
